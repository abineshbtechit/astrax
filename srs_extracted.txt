1. Executive Summary

The Secure Inter-Department Investigation & Legal Document Management System is a centralized platform for investigations involving multiple departments. A crime or legal incident may require police, investigation, forensic, legal and court departments to create separate reports and records. The system creates a common investigation workspace while retaining departmental ownership of each record. Authorized personnel can share a document with a particular person, department, role or investigation participant instead of manually requesting physical copies.

The supplied demo exposes a broad feature set: authentication, dashboard, cases, documents, evidence and chain of custody, investigation timeline, relationship graph, reports, digital signatures, integrity verification, advanced/global search, audit logs, security alerts, notifications, administration, profile/settings and secure document preview. These capabilities form the feature baseline of this SRS. citeturn0view0

2. Purpose

This document defines the complete functional and non-functional requirements for implementing the system with React on the frontend, Spring Boot on the backend and MongoDB Atlas as the persistence platform. 4. Problem Statement and Business Objective

In the existing manual scenario, an investigation can involve multiple departments. Each department prepares its own records. When a person in another department requires one of those records, the person may need to approach the owning department manually. This can delay investigation work and makes access tracking, document version control and accountability difficult.

The proposed system replaces this manual exchange with a controlled digital collaboration model. The investigation is the shared business context; documents remain attributable to their originating department; access is granted explicitly; and all important operations are recorded for accountability.

4.1 Main Objective

Enable authorized personnel from different departments to securely access and collaborate on investigation records without uncontrolled manual document exchange, while preserving ownership, confidentiality, integrity, traceability and evidence custody.

5. Reference Project and Current-State Findings

The uploaded project is named AstraX and contains React/TypeScript frontend code, an Express/Node demonstration server, a Spring Boot backend reference, MySQL schema/seed data, API documentation and security/architecture documentation. The existing backend POM uses Spring Boot 3.2.3 and Java 17, with Spring Web, Spring Security, Spring Data JPA, MySQL, JWT and Apache Tika. The target implementation specified here replaces the relational MySQL persistence layer with MongoDB Atlas.

The existing frontend routing confirms pages for Dashboard, Cases, Case Detail, Documents, Document Detail, Evidence, Evidence Detail, Evidence Chain, Timeline, Relationship Graph, Security, Audit Logs, Reports, Signatures, Integrity Lab, Search, Notifications, Settings, Users, Profile and a demonstration guide. The SRS preserves these business capabilities while restructuring them around the requested production architecture.

The supplied project currently models roles including ADMIN, POLICE_OFFICER, INVESTIGATION_OFFICER, FORENSIC_OFFICER, LAWYER and COURT_OFFICER. It also models case statuses, document types, workflow states, evidence statuses, audit actions, security alerts, notifications and relationship graph entities.

9. Main Business Workflow

User opens the application and completes initial login.

An authorized officer creates an investigation/case for the crime or legal incident.

The case is assigned to the originating department and relevant investigating personnel.

Other participating departments are added to the investigation.

Each department uploads its own reports, evidence records and supporting documents.

Every uploaded document receives ownership, department, classification, hash, version and audit metadata.

When a person in another department needs a record, they use the system to request or receive explicit access rather than manually collecting a copy.

The document owner or designated authority approves the access when approval is required.

The recipient can perform only the actions granted by the permission.

Views, previews, downloads, versions, sharing, approvals, signing and access failures are audited.

Access can expire or be revoked.

Evidence transfers follow a separate custody workflow.

The investigation timeline and relationship graph reflect significant activity.

Authorized users can search records, verify integrity and generate reports.

Final records can be signed/finalized and retained according to policy.

12. MongoDB Atlas SRS

MongoDB Atlas shall replace the current SQL/MySQL metadata model. The SQL tables in the supplied project are a reference for business data, not a requirement to retain relational tables. Large binary documents should preferably be stored in encrypted object storage; MongoDB should store metadata, references, hashes and indexes. GridFS may be used when binary storage inside MongoDB is specifically required.

16. Cross-Department Access Control

This is the core business feature. A document uploaded by Department A is not automatically visible to Department B merely because both departments belong to the same investigation. Access must be explicitly derived from case membership, role policy or an access grant.

Scenario

Expected System Behavior

Department A uploads a restricted report

Report is owned by uploader/Department A and is not automatically exposed to unrelated users.

Department B needs the report

Department B user searches/request access subject to permitted discovery rules.

Owner approves access

A grant is created with recipient and allowed permissions.

Recipient views report

Backend evaluates the grant before returning content.

Recipient downloads report

Download is permitted only if DOWNLOAD permission is active; event is audited.

Grant expires

Access is automatically denied after expiry.

Owner revokes access

Future access is denied immediately; previous audit history remains.

Unauthorized user attempts access

Request is denied and an unauthorized-access audit/security event may be generated.

19. Integrity and Digital Signature Requirements

19.1 SHA-256

Every supported digital file shall receive a server-generated SHA-256 digest. Verification shall calculate the digest from the authoritative stored bytes and compare it with the registered digest. VALID means the values match; TAMPERED means they do not.

19.2 Digital Signatures

Authorized signers shall sign an eligible document/version. The signature record shall contain signer identity, role, document hash, signature value, certificate issuer/provider metadata, status and signing timestamp. Production signatures shall use an approved cryptographic/PKI provider rather than a demonstration-only value.

19.3 Audit Integrity

Each audit record shall contain the hash of the previous audit record and a current record hash derived from canonical event data. Chain verification shall identify whether the sequence is valid and, when possible, the first broken record.

23. Security Requirements

HTTPS/TLS shall be mandatory in production.

JWT secrets/private keys shall never be committed to source control.

Passwords shall use BCrypt, Argon2 or another approved adaptive password hash.

Backend shall enforce authorization on every protected resource.

Access checks shall be performed before metadata and binary content are returned.

Files shall be stored using generated storage keys and sanitized metadata.

Executable/disallowed file types shall be rejected.

File content shall be validated using detected MIME type/content signatures.

Sensitive files shall be encrypted at rest.

Secrets shall be stored in a secret manager/environment configuration.

CORS shall allow only approved frontend origins.

Rate limiting/brute-force protection shall protect login and high-risk APIs.

Security headers and HSTS shall be enabled in production.

Logs shall not contain passwords, JWTs, encryption keys or unnecessary document contents.

Security alerts shall be generated for configured suspicious patterns.

Backups shall be encrypted and recovery tested.

31. Data Governance

Official records shall not be hard-deleted unless organizational policy explicitly permits it.

Archived/sealed records should be read-only.

Access revocation shall not remove audit history.

Retention periods shall be defined by record type and applicable organizational/legal policy.

Backups and replicas shall follow approved data-residency and security requirements.

Production dummy credentials/data shall never be retained.

Personal/sensitive information shall be minimized in logs and search indexes.

32. Assumptions and Constraints

The supplied URL and ZIP are the functional reference baseline; the demo contains dummy data.

The production target is React + Spring Boot + MongoDB Atlas.

The existing MySQL schema is a business-data reference and shall be converted to MongoDB collections.

Production digital signatures require an approved PKI/signature implementation.

Legal admissibility/compliance claims require validation by the deploying organization and applicable legal/security authorities.

Actual department names, permissions, retention rules and approval hierarchy shall be configurable.

Binary storage may be implemented using secure object storage rather than MongoDB itself.

35. Final System Definition

The completed application shall be a secure investigation collaboration platform, not merely a document upload portal. An investigation acts as the shared context for multiple departments. Each department retains attribution and control over the records it creates. Other departments obtain access through controlled authorization rather than informal/manual document exchange. The system combines case management, document lifecycle management, evidence custody, integrity verification, digital signatures, OCR/search, auditability, security alerts, notifications and reporting around this central workflow.

The React frontend shall provide the operational interface; Spring Boot shall enforce business rules and security; MongoDB Atlas shall provide scalable metadata persistence and search; and secure external/object storage or GridFS shall hold document binaries as determined by deployment architecture.
